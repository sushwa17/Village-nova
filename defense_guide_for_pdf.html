1. Unified System Overview (All Team Members Must Know)

Core Pitch & Architecture

30-Second Shared Project Elevator Pitch

VillageNova is an AI-powered, offline-resilient rural intelligence platform designed for Telangana Gram Panchayats and farmers (baseline: Ananthagiri Village, Vikarabad District). Unlike generic LLM chatbots that hallucinate pesticide doses or require high-bandwidth English text, VillageNova unifies multilingual action cards, a deterministic 115-day phenological crop lifecycle state machine, and RAG-grounded PJTSAU 2026 university advisories backed by Supabase Row-Level Security.

End-to-End Request & Intelligence Mechanism

Three Architectural Design Principles Reviewers Love

Design Principle Engineering Mechanism Implemented Why It Matters for Rural Users
1. Determinism Over Pure LLM Guesswork Crop phenology (days elapsed, remaining days, risk severity) is computed deterministically in lifecycle.py and injected into the AI context—never left to LLM math. Prevents dangerous miscalculations of flowering/harvest dates or pesticide timing.
2. Dual-Engine Offline Resilience Flutter Riverpod providers fall back cleanly to local state; FastAPI endpoints return structured fallback responses if DB/Gemini API is unreachable. App never crashes with HTTP 500 errors in 2G/dead-zone agricultural fields.
3. Grounded Action-Card UX Instead of walls of English prose, AI answers return structured JSON ActionItem cards, SourceCitation badges, and plain-language why_advisory explanations. Low-literacy and vernacular farmers can tap clear tasks ("Check drainage bunds") with trust.

How Sushwanth & Rabbani's Phenological Lifecycle State Machine Works

Supervisor & Reviewer Q&A Flashcards — Team B

Sushwanth Q1: "Why did you build a dedicated Python lifecycle service instead of letting Gemini calculate crop stages?"
Model Answer: "LLMs are probabilistic and notoriously unreliable at date arithmetic and domain boundary rules. By building a deterministic state machine in backend/app/services/lifecycle.py, we compute exact elapsed days from the DB sowing date, calculate precise stage completion percentages and transition countdowns, and map biological risks directly from PJTSAU Kharif 2026 standards. Then build_resident_context() injects this deterministic truth into Gemini's context so the AI never hallucinates a farmer's crop stage."
Sushwanth Q2: "Why FastAPI + AsyncSession over Django/Flask, and how did you handle Python 3.12 compatibility?"
Model Answer: "FastAPI's ASGI architecture allows non-blocking async I/O when waiting on external weather/AI calls or PostgreSQL queries via create_async_engine and AsyncSessionLocal. Combined with Pydantic v2 (ConfigDict(from_attributes=True)), every endpoint validates inputs at runtime and generates OpenAPI schemas automatically for Team A. We also standardized all timestamps to timezone-aware datetime.now(timezone.utc), eliminating all Python 3.12 utcnow() deprecation warnings."
Rabbani Q3: "How does authentication work between Supabase Auth on mobile and your FastAPI endpoints?"
Model Answer: "In backend/app/core/security.py, our get_current_user FastAPI dependency intercepts the Authorization: Bearer header and decodes the Supabase JWT using HS256 and SUPABASE_JWT_SECRET with audience authenticated, extracting the resident UUID (sub) and phone number into an AuthenticatedResident object. For offline prototyping and automated pytest runs, it supports explicit dev headers (X-Resident-ID) while enforcing strict 401 rejection when credentials are missing."
Rabbani Q4: "What happens during Resident Onboarding (POST /v1/resident/onboarding)?"
Model Answer: "Onboarding is transactional and multi-role: it resolves or creates the resident's Village, creates/updates ResidentProfile, assigns multiple roles (e.g., farmer, student, shg_livelihood) via ResidentRole, sets up their Farm and initial Crop with computed sowing stage, and automatically seeds role-specific initial tasks in the tasks table—all committed atomically in one async transaction."

  • Dual-Engine AIOrchestrator (backend/app/agents/orchestrator.py): Routes queries through Google's GenAI SDK as the primary reasoning engine (with a 3.5-second HTTP timeout safety bound), backed by a high-precision regional agronomy rule engine that guarantees accurate, cited answers even if the external LLM API is offline or throttled.
  • Function Calling & ToolDispatcher (agents/tools.py & dispatcher.py): Implemented a singleton tool registry with latency profiling and schema validation across 5 specialist domain tools in TOOL_MANIFEST: get_hyperlocal_weather, get_crop_stage_guidance, get_mandi_prices, check_scheme_eligibility, and log_quick_farm_action.
  • PJTSAU & Gazette RAG Grounding (services/knowledge.py): Indexed verified chunks from PJTSAU Kharif 2026 bulletins (Soybean JS-335, Bt Cotton IPM), PM-KISAN/PMFBY guidelines, and Open-Meteo spray advisories with similarity scoring and mandatory SourceCitation attribution.
  • Sub-50ms Semantic Cache & Conversation Guardrails (services/cache.py & conversation.py): Normalizes query keywords scoped by {village}_{crop_name} with a 300-second TTL for instant repeat answers, paired with sliding-window turn truncation and 1,000-character message bounds.

How Team C Prevents Hallucinations (Safety Pipeline)

Supervisor & Reviewer Q&A Flashcards — Team C

Nehith Q1: "How does your RAG system ground answers, and what stops the model from inventing fake citations or toxic pesticide mixtures?"
Model Answer: "We combine two safeguards: First, our knowledge_service retrieves verified document chunks tagged with official authority metadata (such as PJTSAU Kharif 2026 Bulletin #4) and injects them into the reasoning pipeline along with SourceCitation objects containing URLs and timestamps. Second, dosage and stage-specific advisories are encapsulated inside deterministic Python tools registered in ToolDispatcher (e.g., get_crop_stage_guidance), so the LLM executes vetted functions rather than generating chemical ratios from memory."
Nehith Q2: "How does your Semantic Cache achieve <50ms responses without serving stale or cross-crop advice?"
Model Answer: "In backend/app/services/cache.py, SemanticResponseCache.normalize_key() strips punctuation and normalizes tokens, then binds the cache key to a context_scope formed by {village}_{crop_name}. That means a Soybean farmer in Ananthagiri never gets a cached answer meant for a Cotton farmer elsewhere. Cache hits return in ~1–5ms with a 300-second TTL, saving API quota and surviving slow network conditions."
Nehith Q3: "What happens if the Gemini API key is missing, rate-limited, or times out in production?"
Model Answer: "Our AIOrchestrator sets a strict 3500ms client timeout and implements a dual-engine architecture. If the Gemini API fails, times out, or runs in offline/CI test mode, execution seamlessly routes to our regional agronomic fallback engine backed by the same ToolDispatcher and knowledge_service, returning identical AskResponsePayload structures with verified citations and clickable ActionItem cards."
Nehith Q4: "How do you manage multi-turn conversation memory without blowing up token limits?"
Model Answer: "We built conversation_manager in backend/app/services/conversation.py which provisions per-user sessions, enforces MAX_MESSAGE_CHARACTERS validation before inference, and applies sliding-window history truncation so context windows remain bounded and predictable."

5. TEAM D — Data, Infra & Security Defense Playbook

Sahasra

Team D Mission: Architect the zero-trust PostgreSQL database schema on Supabase, enforce Row-Level Security (RLS) isolation across all personal and farm records, harden API endpoints against abuse, and automate continuous integration across backend and mobile codebases.

Sahasra — PostgreSQL Schema, RLS Security, Hardening & CI/CD

  • Normalized Relational Schema (supabase/migrations/20261007000000_initial_schema.sql): Authored the 254-line PostgreSQL schema using uuid-ossp and pgcrypto, custom PostgreSQL ENUM types (resident_role_type, soil_type_enum, water_source_enum, crop_stage_enum), and 15 cascading tables linking villages, profiles, roles, farms, crops, activities, observations, expenses, schemes, tasks, and chat histories.
  • Zero-Trust Row-Level Security (RLS): Enabled RLS across all 14 core tables. Enforced strict owner-only access (auth.uid() = id / auth.uid() = resident_id) on personal profiles, farms, tasks, and conversations while enabling controlled public read policies on verified villages, schemes, and village_updates.
  • API Hardening & Rate Limiting: Paired FastAPI sliding-window rate limiting (check_ask_rate_limit returning HTTP 429) with strict Pydantic input validation and JWT audience checks.
  • Automated GitHub Actions CI/CD (.github/workflows/ci.yml): Maintains the dual-job pipeline on Ubuntu runners executing Python 3.12 (ruff check . + pytest tests/) and Flutter 3.24 (flutter analyze) on every push and PR across develop, staging, and main.

Database Entity-Relationship & Security Isolation Architecture

Table Group Tables in PostgreSQL Schema RLS Security Policy & Integrity Constraint
Identity & Geo villages, resident_profiles, resident_roles villages: public SELECT; resident_profiles: auth.uid() = id; UNIQUE(resident_id, role) prevents duplicate role assignment.
Precision Farm farms, crops, crop_activities, crop_observations, farm_expenses Strict private isolation via auth.uid() = resident_id; ON DELETE CASCADE ensures orphaned crop/expense records never linger.
AI & Operations tasks, conversations, messages (JSONB actions & sources) User-scoped access on tasks and conversations; structured JSONB columns preserve cited action cards for auditability.
Public Intelligence village_updates, schemes, scheme_matches Verified Panchayat notices and government schemes allow public SELECT; personal eligibility scores remain resident-isolated.

Supervisor & Reviewer Q&A Flashcards — Team D

Sahasra Q1: "If an attacker steals the public Supabase anon key from the mobile app, can they read another farmer's land size, expenses, or private chats?"
Model Answer: "No. We enforce defense-in-depth at the PostgreSQL engine layer using Row-Level Security (RLS) in 20261007000000_initial_schema.sql. All sensitive tables—resident_profiles, farms, crops, tasks, and conversations—have ENABLE ROW LEVEL SECURITY active with policies enforcing auth.uid() = resident_id. Even with the public anon key, PostgreSQL rejects unauthorized cross-tenant queries unless authenticated with a valid signed JWT matching the row owner."
Sahasra Q2: "How do you protect the AI endpoints from quota exhaustion, prompt flooding, or DDoS attacks?"
Model Answer: "We implemented two protective controls verified by automated tests in test_ask_hardening.py: First, a FastAPI dependency check_ask_rate_limit enforces a sliding-window rate limiter per resident and returns HTTP 429 Too Many Requests when thresholds are exceeded. Second, message length is capped at 1,000 characters via Pydantic field constraints, preventing token-stuffing attacks."
Sahasra Q3: "How did your CI pipeline catch issues across teams, and what is its current status?"
Model Answer: "Our .github/workflows/ci.yml pipeline runs two independent jobs on every push to develop and main: backend-test (Python 3.12, Ruff static linter, and 65 Pytest unit/integration tests) and mobile-analysis (Flutter 3.24 flutter analyze). Earlier when CI flagged an unused import in farm_provider.dart, the pipeline caught it within 55 seconds, allowing Team A and B to fix it and verify a 100% green build across all squad branches."
